# sat-bruteforce — параллельный перебор 3-SAT на Z7-Lite

Наглядный пример к гипотезе экспоненциального времени (ETH): насколько FPGA ускоряет полный перебор
и почему этого всё равно мало. XC7Z010, только PL, 50 МГц, результат выводится в UART.

## Идея

- 3-SAT с n переменными перебором — это 2ⁿ назначений.
- В FPGA работают P = 2^LOGP одинаковых «ядер». Каждое за такт целиком проверяет одно назначение,
  все клаузы параллельно. Весь перебор занимает **2ⁿ / P тактов**.
- Удвоение числа ядер выигрывает **одну** переменную. 64 ядра = 6 переменных, 1024 ядра = 10.
  Каждая добавленная переменная снова удваивает время.
  Железо уменьшает время в константу раз, а показатель экспоненты остаётся прежним.
  Основание экспоненты уменьшают только алгоритмы (DPLL/CDCL, PPSZ ≈ 1.307ⁿ), а ETH говорит,
  что до 1 + o(1) его не довести.

## Как устроено

Клауза хранится как две маски: `pos[i]` — литерал `xᵢ`, `neg[i]` — литерал `¬xᵢ`.
Назначение `a` выполняет клаузу, если `|((a & pos) | (~a & neg))`.
Маски — константы ($readmemh без порта записи), поэтому синтез сворачивает клаузу в один LUT3,
а формулу — в дерево AND. Ядро `k` фиксирует младшие LOGP бит назначения.
Поэтому клаузы, где все переменные старшие, одинаковы для всех ядер и синтезируются один раз.
Клаузы с младшими переменными упрощаются константами: литерал либо сразу истинен
и клауза исчезает, либо выпадает из клаузы.

```
cnt ──► [P копий формулы] ──► sat_q[P-1:0] ──► [приоритетный шифратор] ──► solution = cnt·P + k
 │          stage 1                                   stage 2
 └─ +1 каждый такт, 2^(n-LOGP) значений
```

Назначения обходятся по возрастанию, поэтому найденное решение — **минимальное**
выполняющее назначение. Именно его ищет эталон в тестбенче.

| Файл | Что |
|---|---|
| `rtl/sat_bruteforce.v` | решатель: счётчик, P ядер, шифратор, счётчик тактов |
| `rtl/uart_tx.v` | UART 8N1 |
| `rtl/top.v` | автозапуск после сброса, кнопка, светодиоды, отчёт в UART |
| `tools/gen_cnf.py` | случайная 3-SAT → `formula.cnf` (DIMACS), `formula.mem`, `formula_params.vh` |
| `tools/read_uart.py` | читает отчёт, проверяет решение по CNF, считает время |
| `tb/run_tb.sh` | Icarus: SAT при LOGP = 0/2/4, UNSAT, top + приём UART |
| `vivado/*.tcl`, `top.xdc` | проект, сборка, прошивка |

## Симуляция

```
cd tb && ./run_tb.sh        # нужны iverilog, python3, numpy
```
Проверяется: решение совпадает с эталоном (минимальное по numpy-перебору) и выполняет все клаузы,
число тактов ≈ a/P, для UNSAT — ровно 2^(n-LOGP)+1, повторный запуск даёт тот же результат,
строка из UART совпадает с внутренним состоянием.

## Железо

```
python3 tools/gen_cnf.py --n 32 --seed 1 --out vivado    # уже лежит в vivado/
cd vivado
vivado -mode batch -source create_project.tcl -tclargs 6   # LOGP=6 -> 64 ядра
vivado -mode batch -source impl.tcl                        # utilization.rpt, timing_summary.rpt, top.bit
vivado -mode batch -source program.tcl
```

Подключение: `uart_tx` выведен на JP2, пин G15 (тот же, что `q` в lesson4). Его соединяют с RX
USB-UART адаптера на 3.3 В, GND с GND. Бортовой USB-UART подключён к PS (MIO), из чистого PL он недоступен.

```
python3 tools/read_uart.py /dev/ttyUSB0 vivado/formula.cnf --logp 6
```

- `led[0]` мигает во время перебора, горит при SAT, гаснет при UNSAT.
- `led[1]` загорается, когда перебор закончен.
- `btn[0]` перезапускает перебор.

Для формулы по умолчанию (n = 32, m = 137, seed 1) по расчёту при 64 ядрах должно прийти
```
SAT   x=0265B1F5 cyc=0000000996C9      # 628 425 тактов = 12.6 мс
```

## Эксперименты

| Формула | P | Тактов | Время на 50 МГц | CPU-перебор, 10⁸/с |
|---|---|---|---|---|
| `--n 32 --unsat` | 64 | 2²⁶ | 1.34 с | 43 с |
| `--n 32 --unsat` | 128 | 2²⁵ | 0.67 с | 43 с |
| `--n 36 --unsat` | 64 | 2³⁰ | 21.5 с | 11.5 мин |
| `--n 40 --unsat` | 64 | 2³⁴ | 5.7 мин | 3 ч |
| `--n 48 --unsat` | 64 | 2⁴² | 24 ч | 33 дня |

UNSAT-формула заставляет перебрать всё пространство. Время детерминированное, поэтому
экспоненту видно в чистом виде: +4 переменные → ×16 времени, ×2 ядра → ÷2.

Что попробовать:
- Увеличивать LOGP (7, 8, …), пока сходится тайминг и хватает LUT. Смотреть `utilization.rpt`
  и WNS: растёт fanout счётчика на все ядра.
- Сравнить с DPLL на той же формуле: `pip install pycosat`. Он решает `--n 32` за миллисекунды на CPU,
  потому что уменьшает основание экспоненты, а не делит время на константу.
- Шаг в сторону настоящих солверов: вынести в FPGA не перебор, а unit propagation
  (параллельная проверка всех клауз при частичном назначении) для CDCL на ARM.

Bitstream в этом коммите не собирался. RTL проверен в Icarus Verilog, `utilization.rpt`
и тайминг появятся после `impl.tcl`.
